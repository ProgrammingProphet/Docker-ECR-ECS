# Stage 4: Docker Storage and Networking

## 1. Container filesystem

- An image is a stack of **read-only layers**. Each container adds a thin **writable layer** on top (copy-on-write).
- Anything written inside the container lives in that layer and **is deleted when the container is removed**.

```bash
docker run -it --name test alpine sh
# inside: echo "hello" > /data.txt ; exit
docker diff test          # shows A /data.txt
docker rm test            # file is gone
docker system df          # see space used by images/containers/volumes
```

**Teaching point:** containers are ephemeral, so anything you need to keep must live outside the writable layer.

## 2. Volumes

Docker-managed storage, stored under `/var/lib/docker/volumes/`. This is the preferred way to persist data.

```bash
docker volume create mydata
docker run -d --name web -v mydata:/usr/share/nginx/html nginx
docker volume ls
docker volume inspect mydata
docker rm -f web
docker volume rm mydata     # only when you really want the data gone
```

- They survive container removal.
- They can be shared between containers.
- They are independent of host directory structure and easy to back up.

## 3. Bind mounts

These map a **specific host path** into the container.

```bash
docker run -d --name web -p 8080:80 \
  -v $(pwd)/site:/usr/share/nginx/html:ro nginx
# or the explicit form:
docker run -d --mount type=bind,source=$(pwd)/site,target=/usr/share/nginx/html nginx
```

| | Volume | Bind mount |
|---|---|---|
| Managed by | Docker | You (host path) |
| Best for | Databases, production data | Dev, live code reload, config files |
| Portability | High | Depends on host layout |
| Path must exist | No | Yes (with `--mount`) |

**Demo:** edit `index.html` on the host and refresh the browser to see the change instantly. Add `:ro` to make the mount read-only.

## 4. Bridge networking

- The default network driver. Containers get a private IP and reach the outside through NAT.
- **Default `bridge`:** containers talk by IP only, with no name resolution.
- **User-defined bridge:** built-in DNS, so containers resolve each other by name, and you get better isolation.

```bash
docker network ls
docker network create mynet
docker network inspect mynet
docker run -d --name web --network mynet -p 8080:80 nginx
```

- `-p host:container` publishes a port to the host. Without it, the container is reachable only from its network.

## 5. Container-to-container communication

```bash
docker network create appnet
docker run -d --name web --network appnet nginx
docker run -it --rm --network appnet alpine sh
# inside:
apk add curl
ping web
curl http://web
```

- Use the **container name as hostname** (for example `db`, `web`).
- Use the container's internal port (80), not the published host port.
- Containers on different networks can't talk unless connected: `docker network connect appnet othercontainer`.

## 6. Persistent database storage

```bash
docker network create appnet
docker volume create pgdata

docker run -d --name db --network appnet \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

docker exec -it db psql -U postgres -c "CREATE TABLE t(id int); INSERT INTO t VALUES (1);"

docker rm -f db                # container destroyed
docker run -d --name db --network appnet \
  -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data postgres:16

docker exec -it db psql -U postgres -c "SELECT * FROM t;"   # data still there
```

For MySQL, the data path is `/var/lib/mysql`. For MongoDB, it is `/data/db`.

**Compose equivalent:**

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [appnet]
  app:
    image: myapp
    ports: ["8080:80"]
    networks: [appnet]
    depends_on: [db]
volumes:
  pgdata:
networks:
  appnet:
```

## Suggested lab flow

1. Prove data loss in the writable layer.
2. Fix it with a named volume.
3. Live-edit a site with a bind mount.
4. Compare default bridge vs user-defined bridge (ping by name fails vs works).
5. Run an app container and a DB container on one network.
6. Destroy and recreate the DB to show persistence.
