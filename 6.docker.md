# Stage 6: Docker in Production, Session Breakdown

You didn't say what you need from this outline, so here is a teaching-ready expansion with the key points and a hands-on lab for each topic.

## 1. Docker Hub
- **Concepts:** registries vs repositories, public vs private repos, official vs verified images, pull rate limits
- **Lab:** create an account, generate an access token (not the password), and run `docker login`

## 2. Image tagging
- **Concepts:** the naming format `namespace/repo:tag`, why `latest` is risky in production, semantic versioning (`1.2.0`), Git SHA tags, digests for immutability
- **Lab:** build one image and tag it `v1`, `v1.0.1`, and `latest` with `docker tag`, then show that they share one image ID

## 3. Pushing and pulling images
- **Concepts:** layers and how the cache is reused on push and pull, private vs public pulls, ECR as the AWS alternative
- **Lab:** push from the laptop, pull on a different machine (EC2 works well), and run it

## 4. Multi-stage builds
- **Concepts:** build stage vs runtime stage, `COPY --from`, `--target`, `.dockerignore`, smaller images and a smaller attack surface
- **Lab:** build the same app with a single-stage and a multi-stage Dockerfile, then compare sizes with `docker images`

```dockerfile
# Build stage
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Runtime stage
FROM node:20-alpine
WORKDIR /app
COPY --from=build /app/dist ./dist
COPY --from=build /app/package*.json ./
RUN npm ci --omit=dev
USER node
EXPOSE 3000
CMD ["node", "dist/index.js"]
```

## 5. Container security basics
- Run as a **non-root user** (`USER`)
- Use **minimal base images** (alpine, slim, distroless) and **pin versions**
- Never bake **secrets** into images or `ENV`; use runtime env vars or a secrets manager
- **Scan images** with Docker Scout or Trivy
- Avoid `--privileged`, and consider `--read-only` and dropping capabilities
- **Lab:** scan an old image (e.g. `node:14`), then fix the findings by upgrading the base image

## 6. Deploy an application on AWS EC2
- **Concepts:** security groups (open only 22 and 80/443), installing Docker, IAM role for ECR pulls, Elastic IP
- **Steps:** launch the instance, SSH in, install Docker, `docker pull`, then `docker run -d -p 80:3000 --restart unless-stopped --name app <image>`
- **Extension:** replace the long `docker run` with a `docker-compose.yml`

## 7. Basic CI/CD integration
- **Flow:** push to GitHub → build image → push to Docker Hub → SSH into EC2 → pull and restart the container
- **Concepts:** GitHub Actions, repository secrets (`DOCKERHUB_TOKEN`, `EC2_SSH_KEY`), tagging with the commit SHA

```yaml
name: build-and-deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USER }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ${{ secrets.DOCKERHUB_USER }}/myapp:${{ github.sha }}
      - uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.EC2_HOST }}
          username: ec2-user
          key: ${{ secrets.EC2_SSH_KEY }}
          script: |
            docker pull ${{ secrets.DOCKERHUB_USER }}/myapp:${{ github.sha }}
            docker rm -f app || true
            docker run -d --name app -p 80:3000 --restart unless-stopped \
              ${{ secrets.DOCKERHUB_USER }}/myapp:${{ github.sha }}
```

## Suggested capstone
Containerize a small app with a multi-stage build and run it as a non-root user. Push it to Docker Hub with a versioned tag, then deploy it to EC2 automatically on every push to `main`.
