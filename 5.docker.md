# Stage 5 – Docker Compose

## What is Docker Compose?

Docker Compose is a tool for defining and running **multi-container applications** using a single YAML file. Instead of typing long `docker run` commands for every container (with ports, volumes, networks, env vars), you describe the whole stack once and bring it up with one command.

**Without Compose:**
```bash
docker network create mynet
docker run -d --name db --network mynet -e POSTGRES_PASSWORD=secret -v dbdata:/var/lib/postgresql/data postgres:16
docker run -d --name web --network mynet -p 8080:80 myapp:1.0
```

**With Compose:**
```bash
docker compose up -d
```

**Why use it:**
- Reproducible environments (same file = same stack for everyone)
- One command to start, stop, or rebuild everything
- Easy to version-control (the file lives in Git)
- Ideal for local development, testing, and small deployments

> Modern Docker uses `docker compose` (v2, a plugin). The older standalone `docker-compose` (v1) is deprecated.

## docker-compose.yml

The default file name is `compose.yaml` or `docker-compose.yml`. The `version:` key at the top is now obsolete and can be omitted.

**Basic structure:**
```yaml
services:      # the containers
  web:
    image: nginx:latest
    ports:
      - "8080:80"

volumes:       # named volumes (optional)
networks:      # custom networks (optional)
```

**Common service keys:**

| Key | Purpose |
|---|---|
| `image` | Image to pull/run |
| `build` | Build from a Dockerfile instead |
| `container_name` | Custom container name |
| `ports` | Host:container port mapping |
| `environment` / `env_file` | Environment variables |
| `volumes` | Mount volumes or bind mounts |
| `networks` | Networks to attach to |
| `depends_on` | Startup order |
| `restart` | Restart policy (`no`, `always`, `unless-stopped`, `on-failure`) |
| `command` | Override the default command |

**Essential commands:**
```bash
docker compose up -d          # create and start in background
docker compose down           # stop and remove containers + networks
docker compose down -v        # also remove volumes
docker compose ps             # list services
docker compose logs -f web    # follow logs of a service
docker compose build          # build images
docker compose up -d --build  # rebuild and start
docker compose exec web sh    # shell into a running service
docker compose config         # validate and view the final config
```

## Multiple Containers

A typical stack: web app + database + cache.

```yaml
services:
  web:
    build: ./app
    ports:
      - "5000:5000"
    depends_on:
      - db
      - redis

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - dbdata:/var/lib/postgresql/data

  redis:
    image: redis:7

volumes:
  dbdata:
```

Run it: `docker compose up -d`

**Key point:** Services can reach each other **by service name**. Inside `web`, the database host is simply `db` and Redis is `redis`, with no IP addresses needed. Compose provides built-in DNS.

**Scaling a service:**
```bash
docker compose up -d --scale web=3
```
(Don't hard-code `container_name` or a fixed host port if you plan to scale.)

## Environment Variables

**1. Inline in the file:**
```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
```

**2. From an `.env` file** (automatically read for variable substitution):
```bash
# .env
DB_PASSWORD=secret
APP_PORT=8080
```
```yaml
services:
  web:
    image: myapp
    ports:
      - "${APP_PORT}:80"
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

**3. Using `env_file`** (loads all variables into the container):
```yaml
services:
  web:
    image: myapp
    env_file:
      - ./web.env
```

**4. Default values:**
```yaml
ports:
  - "${APP_PORT:-8080}:80"     # use 8080 if APP_PORT is unset
```

**Best practices:**
- Add `.env` to `.gitignore`, and commit a `.env.example` instead
- Never hard-code real passwords in the YAML
- For production, use Docker **secrets** or a secrets manager

## Service Dependencies

`depends_on` controls **start order**.

```yaml
services:
  web:
    build: .
    depends_on:
      - db
  db:
    image: postgres:16
```

**Problem:** the basic form only waits for the container to *start*, not for the app inside to be *ready*. Postgres may still be initializing when `web` tries to connect.

**Solution: health checks + condition:**
```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: secret
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  web:
    build: .
    depends_on:
      db:
        condition: service_healthy
```

**Conditions:**
- `service_started` (default)
- `service_healthy` (waits for a passing healthcheck)
- `service_completed_successfully` (for one-off init/migration jobs)

Also add `restart: on-failure` or retry logic in the app as a safety net.

## Networks and Volumes

### Networks

By default, Compose creates one network for the project, and all services join it and can talk by name. Custom networks let you **isolate** services.

```yaml
services:
  web:
    image: nginx
    ports:
      - "80:80"
    networks:
      - frontend

  api:
    build: ./api
    networks:
      - frontend
      - backend

  db:
    image: postgres:16
    networks:
      - backend      # not reachable from web directly

networks:
  frontend:
  backend:
```

Here `web` can reach `api`, and `api` can reach `db`, but `web` cannot reach `db`.

### Volumes

Containers are ephemeral; volumes persist data.

**Named volume (managed by Docker, best for databases):**
```yaml
services:
  db:
    image: postgres:16
    volumes:
      - dbdata:/var/lib/postgresql/data

volumes:
  dbdata:
```

**Bind mount (host folder, best for development/live code reload):**
```yaml
services:
  web:
    build: .
    volumes:
      - ./src:/app/src
      - ./nginx.conf:/etc/nginx/nginx.conf:ro   # read-only
```

**Useful commands:**
```bash
docker volume ls
docker volume inspect <project>_dbdata
docker compose down -v      # removes named volumes too (data loss!)
```

## Complete Example: Flask + PostgreSQL + Redis

```yaml
services:
  web:
    build: ./app
    ports:
      - "${APP_PORT:-5000}:5000"
    environment:
      DATABASE_URL: postgresql://admin:${DB_PASSWORD}@db:5432/appdb
      REDIS_HOST: redis
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - frontend
      - backend
    restart: unless-stopped

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: appdb
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U admin -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 5
    networks:
      - backend

  redis:
    image: redis:7
    networks:
      - backend

volumes:
  dbdata:

networks:
  frontend:
  backend:
```

`.env`:
```
DB_PASSWORD=supersecret
APP_PORT=5000
```

**Run:**
```bash
docker compose up -d --build
docker compose ps
docker compose logs -f web
docker compose down
```

## Quick Summary

| Concept | Key takeaway |
|---|---|
| Compose | Define and run multi-container apps from one YAML file |
| `docker-compose.yml` | `services`, `volumes`, `networks` are the top-level blocks |
| Multiple containers | Services talk to each other by service name |
| Environment variables | Use `environment`, `env_file`, or `.env` with `${VAR}` |
| Dependencies | `depends_on` + `healthcheck` for real readiness |
| Networks | Isolate tiers (frontend/backend) |
| Volumes | Named volumes for persistent data, bind mounts for dev |
